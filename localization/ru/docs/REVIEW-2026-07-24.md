# Проверка кода — 2026-07-24

Проверка закоммиченного кода M0–M3 и незакоммиченной работы M4 (`planes.js`,
переписанный `fins.js`). Пункты упорядочены по важности; ошибки 1–2 исправить
до следующей проверки M4 в браузере.

## Ошибки

- [x] *(ИСПРАВЛЕНО 2026-07-25)* **1. Смещение плоскости `d` в `fitPatch` равно ⅓ истинного — БЛОКИРУЕТ M4.**
  `planes.js`, примерно строки 148–156: `wSum += area[f]` находится внутри цикла по 3 вершинам,
  поэтому `wSum` становится равной 3·Σarea, но делитель — `wSum * 3`, то есть 9·Σarea,
  при числителе 3·Σ(area·projection). Плоскость каждого участка оказывается на одной трети
  истинного расстояния от начала координат; отклонение от плоскости считается относительно
  того же неверного `d`, поэтому `dev` превышает `FLAT_TOL` и почти все участки отклоняются.
  **Симптом в браузере:** «нет достаточно высокой плоской вертикальной грани» на деталях,
  где такие грани явно есть.
  **Исправление (одна строка):** `const d = dSum / wSum;` (либо вынести приращение `wSum`
  из внутреннего цикла и оставить `* 3`).

- [x] *(ИСПРАВЛЕНО 2026-07-25 — контакт теперь берётся из вершин ниже BED_EPS)* **2. Площадка и вектор наклона исчезают именно при наклоне на ребро.**
  `fins.js`, примерно строки 304–324: `contact` собирается только из вершин граней с признаком
  `onBed`. У детали на ребре — основного сценария, где контакт со столом ≈ 0 — **нет** граней,
  у которых самая высокая вершина ниже `BED_EPS`, поэтому `contact` пуст. Последствия:
  `buildPad` возвращает null (нет площадки у детали, которой она нужнее всего); показатели
  (`app.js`, примерно 418) пишут «не нужна», то есть обратное действительности; `tip` остаётся
  null, поэтому член выравнивания `scorePatches` равен нулю и рёбра не направляются
  в сторону падения.
  **Исправление:** определять контакт по объединённым *вершинам* с z < ε (в топологии уже есть
  всё нужное), а не по принадлежности целых граней столу.

- [x] *(ИСПРАВЛЕНО 2026-07-25 — analysisTiming хранится как значение)* **3. Строка времени в статистике накапливается.**
  `updateFinReadout` дописывает через `el('s-time').textContent += …` (`app.js`, примерно 440).
  Это верно при вызове через `shade()` (она сбрасывает строку), но обработчики выбора режима,
  площадки и рёбер вызывают `refreshFins()` напрямую: каждое переключение добавляет ещё
  «· рёбра N мс» без сброса.

- [ ] **4. Проверка габаритов не учитывает рёбра и площадку.** `report()` (`app.js`, примерно
  329–336) сравнивает с областью печати только габариты детали. Но экспорт включает площадку,
  эллипс которой выступает за контакт на `padMargin` (4 мм) и может выйти за край стола,
  хотя деталь «помещается». При включённых рёбрах расширить проверяемые границы
  по `finTris`/`padTris`.

- [x] *(ИСПРАВЛЕНО 2026-07-25 — защита от вырожденных треугольников по площади проекции)* **5. `patchCovers` возвращает true для вырожденных треугольников.**
  `planes.js`, примерно 198–204: у треугольника нулевой площади d1=d2=d3=0, поэтому `neg`
  и `posv` оба false → «внутри». Один такой треугольник делает проверку покрытия всегда
  успешной и возвращает перемычки в воздухе, от которых функция должна защищать.
  Защита: пропускать треугольники с площадью проекции ~0.

- [x] *(ИСПРАВЛЕНО 2026-07-25)* **6. Косметика:** длинное тире в заголовке STL (`stl.js`, примерно 27)
  после маски `& 0x7f` превращается в управляющий байт 0x14. Использовать обычный дефис.

## Отступления от собственной спецификации — нужно решение

- [ ] **Стенка занимает весь участок, хотя спецификация требует кромку или угол.** FIN-SPEC:
  «размещать на кромке или углу, никогда в середине грани», но `buildFin` вытягивает стенку
  по всему участку (`fins.js`, примерно 118, `uA..uB`) с перемычками через каждые 14 мм
  по всей ширине. На крупной грани это стенка длиной 100+ мм со следами посреди видимой
  поверхности, а у `FIN` нет `maxLen`. Рассмотреть ограничение длины стенки (пропорционально
  высоте, возможно 15–25 мм) и привязку к *концу* участка (углу), а не к центру.
- [ ] **Высота слоя и ширина сопла должны стать параметрами вызова, а не глобальными значениями.**
  План уже говорит, что размеры зависят от этих входных параметров, но в `FIN` жёстко заданы
  `tineH: 0.3` / `tineW: 0.5` как глобальные значения модуля. При добавлении полей не меняйте
  `FIN`: пусть `buildFins` принимает `{...FIN, ...overrides}` при каждом вызове.
  Это сохранит возможность использовать геометрическое ядро вне текущего интерфейса.
- [ ] **Индикатор замкнутости сетки есть в разделе загрузки плана, но не реализован.**
  Почти бесплатно: `buildTopology` уже строит карту рёбер; непарные рёбра — граничные,
  число границ == 0 даёт индикатор. Около ~10 строк и полезный признак надёжности.

## Архитектура (сохранить удачные решения)

Разделение слоёв правильное, его стоит защитить: `overhangs.js` / `planes.js` /
`fins.js` / `writeBinarySTL` — чистая геометрия без зависимостей от DOM и three.js;
`app.js` связывает всё вместе. Обход граней всех четырёх тел (стенка, основание,
перемычки, площадка) проверен и направлен наружу.

- [ ] **Разделить `app.js` ДО M5, а не после.** 740 строк смешивают настройку сцены,
  манипулятор и укладку щелчком, сохранение области печати, интерфейс рёбер, экспорт
  и перетаскивание файлов; около ~15 общих изменяемых значений верхнего уровня.
  Режим ручного размещения добавит автомат состояний указателя к уже существующим
  наведению, нажатию и манипулятору (примерно строки 540–585 уже жонглируют четырьмя состояниями).
  Выделить `viewer.js` (сцена, камера, свет, стол), `orientation.js` (манипулятор и выбор грани),
  `volume.js` (предустановки и localStorage); app.js только связывает их.
- [ ] **JSDoc `@typedef` для четырёх основных структур** (Topology,
  AnalysisResult, Patch, результат buildFins). Сейчас контракты только текстовые;
  typedef даст проверки IDE без этапа сборки.
- [ ] **`tests.html` — страница тестов в браузере без node.** Импорт чистых модулей,
  проверки на маленьких синтетических сетках (куб, клин 45°, L-образная грань для
  `patchCovers`). Поймала бы ошибку #1. Защитит численное поведение (эпсилон при 45°,
  аппроксимацию участков) от регрессий.
- [ ] **Отвязать `buildTopology` от three.js**: принимать массив координат вместо
  BufferGeometry (читается только `getAttribute('position').array`).

## Возможные функции (в плане их нет, но они стоят своего кода)

- [ ] **Расход материала на рёбра («рёбра добавят ~2.3 г»).** Замкнутые тела → объём
  считается по теореме о дивергенции суммой по уже созданным треугольникам. Подтверждает
  обещание меньшего расхода, помогает проверить обещание ускорения и показывает цену
  выбора между стабилизацией и покрытием нависаний. Здесь это максимальная польза на строку.
- [ ] **Отмена ориентации (Ctrl+Z).** Одного сброса мало, если укладка щелчком выбрала
  неверную грань; стек кватернионов с записью на каждое действие, около ~15 строк.
- [ ] **Распознавание дюймов.** Габариты меньше ~5 мм → вопрос «похоже на дюймы —
  увеличить в ×25.4?».
- [ ] **Ориентация в URL вместе с `?stl=`.** Общая ссылка точно воспроизводит сцену:
  отчёты об ошибках, видео и ссылки авторов «вот как печатать мою модель»
  (способ выйти на аудиторию Printables/MakerWorld).
- [ ] **Кнопка снимка экрана.** Вид с красными нависаниями лучше всего подходит для снимков:
  `canvas.toBlob` и повторная отрисовка. Естественный способ делиться приложением.
- [ ] **Перенести кнопку примера модели из M7 на более ранний этап.** `loadURL` и
  `dev-models/` уже есть; сам план называет это «разницей между уходом со страницы и первым
  экспортом». Час работы, а не отдельный этап.
- [ ] **Экспортировать сопроводительный отчёт** (`.txt` рядом со STL либо в 80-байтовом
  заголовке и имени файла): что добавлено, предполагаемая ориентация, «поддержки слайсера
  не нужны». STL распространяется без нас.

## Оценка самого плана

Порядок M4→M7 разумен: стабилизация перед покрытием нависаний, запрос разрешения в интерфейсе
перед изменением детали. Выбор размещения через режим — самое сильное продуктовое решение
в документах. Структурные изменения не рекомендуются.
