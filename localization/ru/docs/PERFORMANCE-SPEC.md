# Спецификация: ускорение генерации поддержек для крупных и неудачно ориентированных деталей

Самодостаточная задача для новой сессии. Инструмент уже не блокирует интерфейс (генерация
работает в Web Worker), но одно построение для крупной или неудачно ориентированной детали
всё ещё может занимать **~2–4 с**. Цель — заметно ускорить само построение **без изменения
получаемой геометрии и ухудшения качества печати.**

## Где находится код

Репозиторий: `~/projects/support-fins` (продукт **Support Fins**). Движок генерации — чистая
математика полигональных сеток (без DOM/three.js), поэтому запускается и профилируется
в Deno без графического интерфейса.

- `web/fins.js` — входная функция `buildFins()`; автоматический режим рекурсивно вызывает
  `mode:'prop'`, затем добавляет клинья (`buildPerpFins`, `web/fins/wedges.js`) и опорную
  площадку (`buildPad`, `web/fins/pad.js`).
- `web/prop.js` — `buildProps()`, управляющая этапами построения каждой стенки в
  `web/prop/`: `splitRegion`/`patchTracks` (`tracks.js`), `sweep` (`sweep.js`),
  `settleTop`/`contourTop`/`lowerSag` (`contact.js`), `stationIsClear`/`stationCertified`
  (`clearance.js`), `emitTines` (`tines.js`), `surfaceZAt` (`surface.js`, уже ускорена
  пространственной сеткой).
- `web/inside.js` — `insidePart`, `nearestPart` (обе ускорены сеткой 64² в плоскости YZ).

Запуск без интерфейса: `deno run --allow-read <script.js>` (пример профилирования ниже).

## Проблема и её воспроизведение

Пользовательский `flat_bracket.stl` (~311×120×192 мм, всего **2,048 треугольников**),
уложенный **плашмя**, строится за ~2.4 с и создаёт 16 стенок поддержки / 576 перемычек.
Та же деталь в удачной ориентации (например, 45°) строится за **~60–100 мс** с 9 рёбрами.
Значит, причина не в количестве треугольников: плохая ориентация создаёт ~16 высоких стенок,
а объём работы для каждой стенки растёт с её высотой.

Инструмент уже *подсказывает* более удачную ориентацию («Предложить ориентацию», карточка
прочности и оценки), а Web Worker сохраняет отзывчивость интерфейса с индикатором ожидания.
Эта задача касается вычислений в случаях, которые всё ещё обрабатываются медленно.

## Что уже измерено (начните отсюда и уточните)

Измерено на `flat_bracket.stl` плашмя, `buildFins(mode:'auto', bedPad:true,
tines:true, tineDensity:0, coverage:0)`, всего ~2.4–2.5 с:

- **Геометрические примитивы ≈ 20%**: `insidePart` ~240 мс / **1.28 млн вызовов**,
  `nearestPart` ~240 мс / ~280 тыс. вызовов, `surfaceZAt` ~32 мс / ~110 тыс. вызовов.
- **Именованные функции отдельных сечений ≈ 19%**: `stationCertified` ~230 мс,
  `stationIsClear` ~200 мс, `settleTop`/`contourTop`/`lowerSag` вместе ~15 мс.
- **Остальные ≈ 60% ещё не распределены по функциям**: это остальные этапы построения стенок
  (`sweep`, `patchTracks`/`splitRegion`, тело цикла `buildProps`, `emitTines`, `buildPad`,
  `buildPerpFins`) и накладные расходы JS на итерации циклов проверки (управление циклом,
  `profileHalf`, выделение массивов), а не сами вызовы примитивов. **Точно определить,
  куда уходят эти 60%, — шаг 1**. Не оптимизируйте, пока не выясните конкретную функцию.

Изолированные проверки: отключение площадки сэкономило ~200 мс; отключение перемычек —
~250 мс. Вместе это ~450 мс; основное время уходит на построение самих стенок.

### Метод профилирования (работает и с досрочными возвратами)

Оберните функцию через переименование: замените `export function foo(` на `function _foo(`,
затем добавьте экспортируемую обёртку с замером времени. Пример:

```js
globalThis.__T = globalThis.__T || {};
const _tw = (name, fn) => (...a) => { const t = performance.now(); const r = fn(...a); globalThis.__T[name] = (globalThis.__T[name]||0) + (performance.now()-t); return r; };
export const sweep = _tw('sweep', _sweep);
```

Скрипт замера (`deno run --allow-read prof.js`):

```js
const WEB='/Users/matthewtrahan/projects/support-fins/web';
const { buildTopology, analyze } = await import(`${WEB}/overhangs.js`);
const { buildFins } = await import(`${WEB}/fins.js`);
function readSTL(b){const dv=new DataView(b.buffer,b.byteOffset,b.byteLength);const n=dv.getUint32(80,true);
  const p=new Float32Array(n*9);for(let f=0;f<n;f++){const o=84+f*50+12;for(let i=0;i<9;i++)p[f*9+i]=dv.getFloat32(o+i*4,true);}return p;}
const pos=readSTL(Deno.readFileSync('/tmp/fb.stl'));       // copy flat_bracket.stl to /tmp/fb.stl
const topo=buildTopology({getAttribute:k=>k==='position'?{array:pos}:null});
const rot=[1,0,0,0,1,0,0,0,1];                              // flat; the slow pose
const res=analyze(topo,45,rot);
globalThis.__T={};
const t=performance.now();
buildFins(topo,res,rot,{mode:'auto',bedPad:true,tines:true,tineDensity:0,coverage:0});
console.log('total',(performance.now()-t).toFixed(0),'ms', globalThis.__T);
```

(`flat_bracket.stl` находится в пользовательском `~/Downloads`; попросите файл либо возьмите
любую крупную деталь плашмя. `web/dev-models/` исключён из git: туда можно положить тестовый
STL и открыть его в браузере через `?stl=dev-models/x.stl`.)

## Возможные подходы (по сочетанию безопасности и эффекта; проверяйте каждый отдельно)

1. **Сначала найдите, куда уходят неучтённые ~60%** (выше). Оптимизируйте функцию,
   которая действительно их расходует, по измерениям, а не догадкам.
2. **Грубая ранняя проверка целой стенки (вероятно, наибольший безопасный выигрыш).**
   До проверки каждого сечения по всей высоте выполните ОДИН дешёвый запрос ограничивающего
   параллелепипеда коридора стенки к сетке `inside.js`: если в нём нет треугольников детали,
   кроме поддерживаемого нависания, полный проход `stationIsClear` / `stationCertified`
   по высоте заведомо тривиален и его можно пропустить. Под плоской деталью с большим открытым
   нависанием большинство стенок находится в воздухе, поэтому исчезнут целые группы итераций.
   Проверка должна быть точной, а результат — идентичным.
3. **Объедините два прохода по всей высоте.** `stationIsClear` (путь до стола) и
   `stationCertified` (проверка сплавления) отдельно проходят всю высоту каждого сечения
   (здесь примерно по ~2,900 вызовов). Общий проход даст ~2× на этом участке.
   Они проверяют разные свойства, поэтому действуйте осторожно.
4. **Распараллельте работу на небольшом пуле воркеров.** Разделите стенки и области между
   N воркерами и объедините выходные треугольники. Почти линейное ускорение на нескольких
   ядрах без изменения геометрической математики (минимальный риск ошибки), но больше всего
   инфраструктурного кода. Отправная точка — текущий воркер (`web/finworker.js`).
5. **Микрооптимизируйте внутренние циклы.** Вынесите `profileHalf`, уберите выделение массивов
   на каждой итерации, используйте типизированные массивы и плоские числовые циклы в `sweep`,
   `settleTop` и веерах проверок. В лучшем случае ~1.3–1.5×; только там, куда указывает профиль.
6. **Адаптивная плотность сечений и проверок по z для очень высоких стенок** — КРАЙНЯЯ мера.
   Для шага сечений 1.0 мм и шага проверок по z ~1.5 мм документирована история регрессий
   со сплавлением (см. комментарии в `stationIsClear`/`stationCertified`/`PROP.stationStep`).
   Увеличение шага опасно привариванием поддержек. Нужны убедительные защитные проверки.

## Жёсткие ограничения

- **Результат должен быть идентичным (или доказуемо эквивалентным).** На тестовом наборе
  количество рёбер и перемычек и замкнутость сеток не должны меняться. Задача — ускорение,
  а не изменение поведения. См. `project_support_fin_quality_first`: никогда не ухудшайте
  качество печати ради экономии времени.
- Учитывайте историю регрессий со сплавлением при проверках сечений (подход 6).

## Защитные проверки

- **Модульные тесты:** `deno test --allow-read tests/` — должно остаться **30 успешных / 0 ошибок**.
- **Стресс-набор:** `deno run --allow-read prototype/stress/run.js` — должно остаться
  **146 OK / 0 WARN / 1 FAIL** (1 FAIL — существующая исходная ошибка тора плашмя).
- **Идентичность результата:** до и после запустите `buildFins` на разных деталях
  (`web/dev-models/*` и flat_bracket плашмя), убедитесь, что число рёбер, перемычек
  и треугольников не изменилось, а поддержки остались замкнутыми.
- **Замер скорости:** измерьте время скриптом выше до и после; отдельно сообщите ускорение
  для положения плашмя.

## Критерии приёмки

- Построение `flat_bracket.stl` плашмя заметно быстрее: цель **минимум 2×**
  (в идеале меньше ~800 мс), по измерению скриптом.
- Количество рёбер, перемычек, треугольников и замкнутость сеток на тестовом наборе не изменились.
- Модульные тесты 30/30, стресс-набор 146 OK / 1 FAIL (исходный), ошибок в консоли приложения нет.

## Уже реализовано (для контекста, не повторяйте)

- `surfaceZAt` ускорена сеткой (XY-ячейки кешируются для каждого массива tris).
- Генерация работает в Web Worker; ползунки используют задержку; новое положение заменяет
  незавершённое построение. Пробовали ранний выход через `nearestPart` в `stationIsClear`,
  но **откатили**: вызовов `insidePart` стало меньше, однако `nearestPart` стоила столько же,
  и выигрыша не было. Расходы даёт *итерация* цикла, а не примитив; поэтому подходы 2–5
  сокращают число итераций, а не стоимость примитива.
